HC-SR04 Wrong Distance Readings? How to Diagnose Them with Arduino

A practical workflow for investigating zero readings, sudden jumps and measurements that do not match a ruler. Test the sensor, target and timing before changing your project logic.

An HC-SR04 can show a distance that jumps, stays at zero or differs from a ruler even when the Arduino sketch uploads successfully. The useful first step is to separate a sensor problem from a wiring, target or timing problem. If you are still choosing a module or learning the broader distance-sensing basics, Vayuyaan's ultrasonic sensor quick-start guide provides that background; this article concentrates on diagnosing an HC-SR04 already connected to an Arduino.

This is a focused companion to the HC-SR04 pinout, wiring and Arduino code guide. Use that guide for the four-pin connection and basic distance formula. Use this one when the readings from your own setup are unreliable.

1. Start with a controlled test

Do not begin by changing several lines of code at once. First create a repeatable setup so one variable changes at a time.

  1. Disconnect power before checking or moving jumper wires.
  2. Confirm VCC, GND, TRIG and ECHO against the pin labels on your exact module. The pin numbers in the sketch must match the wiring.
  3. For an ordinary HC-SR04 module, use its specified supply voltage. A typical HC-SR04 is used with a 5 V supply; check the module documentation for your version.
  4. Place a broad, flat, hard target in front of the two transducers. Keep its face approximately perpendicular to the sensor rather than pointing it away.
  5. Begin at a moderate distance within the sensor's nominal operating range, then compare readings with a ruler.
  6. Keep the sensor and target still while collecting a short series of readings.

IMPORTANT

Do not test first against fabric, foam, a narrow rod or a sharply angled surface. These targets may return a weak echo. A failed echo does not automatically mean the sensor is defective.

2. Upload a diagnostic sketch

This sketch deliberately does only one job: trigger the sensor, measure the ECHO pulse with a timeout, and print the raw pulse duration alongside the calculated distance. It uses TRIG on D9 and ECHO on D10 as example pins. Change both the wiring and constants together if your project uses different pins.

const byte TRIG_PIN = 9;
const byte ECHO_PIN = 10;

const unsigned long ECHO_TIMEOUT_US = 30000UL;
const float SOUND_SPEED_CM_PER_US = 0.0343f;

void setup() {
  Serial.begin(9600);
  pinMode(TRIG_PIN, OUTPUT);
  pinMode(ECHO_PIN, INPUT);
  digitalWrite(TRIG_PIN, LOW);
}

void loop() {
  // Send the trigger pulse.
  digitalWrite(TRIG_PIN, LOW);
  delayMicroseconds(2);
  digitalWrite(TRIG_PIN, HIGH);
  delayMicroseconds(10);
  digitalWrite(TRIG_PIN, LOW);

  // pulseIn returns 0 when no complete pulse arrives before timeout.
  unsigned long echoUs =
      pulseIn(ECHO_PIN, HIGH, ECHO_TIMEOUT_US);

  if (echoUs == 0) {
    Serial.println("No echo: inspect wiring, target and range");
  } else {
    float distanceCm =
        (echoUs * SOUND_SPEED_CM_PER_US) / 2.0f;

    Serial.print("Echo: ");
    Serial.print(echoUs);
    Serial.print(" us | Distance: ");
    Serial.print(distanceCm, 1);
    Serial.println(" cm");
  }

  // Allow the previous burst and reflections to die away.
  delay(60);
}

What the serial output tells you

  • No echo: the timeout was reached before a complete HIGH pulse was measured. Check wiring, pin selection, target reflection and distance.
  • Echo time changes but distance does not: check that the sketch being uploaded is the same one you are reading, and that the Serial Monitor is showing the correct board and port.
  • Echo time is stable but the displayed distance is wrong: inspect the calculation, units and ruler setup before replacing the sensor.

The Arduino pulseIn() reference explains that the function measures the duration of a pulse and returns zero if no complete pulse is received before the timeout. A zero return is therefore a timeout indicator, not a valid measurement of zero centimetres.

4. Check trigger timing, timeout and repeated measurements

For the commonly used HC-SR04, example sketches send a trigger pulse of about 10 microseconds. The echo timeout should be long enough for the maximum distance you actually need, but not so long that a missing echo stalls the rest of the program. The 30 ms timeout in the diagnostic sketch is a practical example, not a universal value for every ultrasonic module or application.

Leave a gap between measurements. Sending another burst too soon can make the next reading harder to interpret because earlier sound may still be travelling or reflecting. The 60 ms delay in the example is a conservative interval for a basic test. For a robot that needs faster updates, test the sensor and environment at the intended rate instead of assuming a delay is always sufficient.

Use a median to reduce occasional outliers

When the target is stationary, collect several valid distance samples, sort them and use the middle value. Ignore timeout samples rather than treating them as zero distance. A median can reduce the effect of occasional outliers; it cannot correct a consistently wrong distance caused by an incorrect formula, mounting angle or unsuitable target.

// Example: median of five valid readings after collecting them.
// Store only successful measurements; do not store timeout zeros.
float readings[5] = {
  49.8, 50.2, 83.1, 50.0, 49.9
};
// Sort the five values in ascending order before using:
float medianCm = readings[2]; // 50.0 cm for this illustrative sorted set

The values above are an illustrative example, not measured sensor results. In a real sketch, check that five valid samples were collected and sort the array before selecting its middle element.

5. Check accuracy with a simple measurement log

Use the same flat target and keep its face and the sensor fixed. Compare the sensor with a ruler at several distances that matter to your project. Record actual results instead of assuming the module has a fixed accuracy under all conditions.

If the error grows with distance, review the measurement setup and the assumed speed of sound. If the readings are consistently offset by a similar amount, check where the ruler starts and where the sensor's transducer face is positioned. These are different patterns and should not be treated with the same software adjustment.

6. Make the reading safer to use in a project

A distance sensor should not be the only safeguard for a moving mechanism. For a robot or automatic lid, decide what the program should do when there is no echo, an out-of-range value or a sudden implausible jump. Do not interpret a timeout as “object is at zero centimetres,” and do not let one bad sample trigger a motor.

  • Define a valid measurement range for the specific application.
  • Handle timeout and invalid values as a separate state.
  • Require more than one consistent reading before a non-critical action when the application allows it.
  • Stop or enter a safe state if the sensor data becomes unavailable; do not rely on smoothing as a safety mechanism.
  • Test the complete assembly with motors and moving parts secured, and keep hands clear during powered tests.

Frequently asked questions

Why does my HC-SR04 show zero?

In sketches using pulseIn(), a returned value of zero normally means the expected pulse was not measured before the timeout. It does not mean the target is at zero centimetres. Check the wiring, pin mapping, target and timeout handling.

Why does the HC-SR04 give different readings for the same object?

The target may be angled, soft or too small, or there may be nearby reflecting surfaces. Loose connections and electrical or mechanical noise can also affect a project. Test with a fixed, flat target before changing the code.

Should I average HC-SR04 readings?

Repeated valid samples can help you understand variation. A median can reduce the influence of occasional outliers, but filtering does not repair systematic errors or make an unsuitable target detectable.

How often should I trigger an HC-SR04?

Leave time for the previous ultrasonic burst and its reflections to die away. The appropriate interval depends on the required range, the module and the environment. Start with a conservative interval such as the 60 ms used in this basic diagnostic sketch, then test the actual application.

Can I connect the HC-SR04 ECHO pin directly to an ESP32?

Do not assume it is safe. A typical HC-SR04 ECHO output can be around 5 V, while ESP32 GPIO inputs are generally 3.3 V. Check the exact board specifications and use an appropriate level shifter or voltage divider when required.
